# Soma

Runner Windows nativo en Rust. GUI y CLI comparten una única autoridad de ejecución mediante IPC local. Usá `soma-cli help` y sus respuestas JSON para operar la app.

`model.rs` posee configuración, entorno y vigencia de builds; `engine.rs`, operaciones, logs y árboles de procesos; `jobs.rs`, cola, participaciones y resultados; `reports.rs`, evidencia Surefire/Failsafe; `jobs_cli.rs`, comandos de trabajos; `worker.rs`, consola y Ctrl+C; `ipc.rs`, protocolo; `ui.rs`, controles Win32. Conservá las colas acotadas y el control de reentrada del visor. [GLOSSARY.md](GLOSSARY.md) define el dominio.

Para levantar una aplicación, elegí el checkout con `run --path DIRECTORIO`, guardá el `operation_id` y usá `wait --operation ID --ready` para comprobar disponibilidad. Detené únicamente la ejecución que iniciás mediante `stop --operation ID`. `--wait` sigue esperando la finalización del proceso. Consultá README para readiness, variables explícitas y selección de rama/worktree. Las pruebas y compilaciones específicas conservan sus herramientas y políticas locales.

Para tests y compilaciones finitas de proyectos Maven registrados usá `jobs submit --path DIRECTORIO --config tests --kind test|build -- ARGUMENTOS_MAVEN`. Conservá `job_id` y `participant_id`, consultá `jobs wait/status/logs` y retirate con `jobs release --job ID --participant ID`. No canceles participaciones de otros. Un timeout no cancela; no cierres una ventana compartida para cancelar tu trabajo. `jobs status ok:true` solo confirma la consulta; validá el resultado de `jobs wait` y su evidencia. Los trabajos siguen usando el Wrapper y el adaptador configurado. Revisá el entorno separado de `test_configs`, sus proveedores y el alcance de los tests antes de enviarlos. Si hay política local de recursos, mantené el adaptador que la aplica y evitá launchers anidados.

La precedencia de variables de ejecución es sistema → `.env` → overrides explícitos. Las pruebas usan su propia configuración; no heredan automáticamente el `.env` ni los parámetros JVM del runtime. Los datos personales viven en `%USERPROFILE%\.soma`, salvo configuración portable existente, `SOMA_HOME` o `--data-dir`. Conservá entradas ajenas al editar `projects.json`; ejecutá `validate` después. `snapshot:true` solo corresponde a JAR autocontenido; no aísla bases de datos, archivos externos ni puertos.

Para validar cambios de ejecución, `tests/verify.ps1` ejercita la CLI con JVMs reales descartables. `tests/targets.ps1` verifica worktrees, cambios de rama, IDs de ejecución y readiness contra servidores Java reales. `tests/jobs.ps1` verifica coordinación, evidencia y cierre con Maven/JUnit reales. `tests/distribution.ps1` verifica almacenamiento entre versiones y el ZIP público. `cargo test` protege lectura de evidencia XML adversa. Respetá los controles de recursos de la máquina local; CI compila y prueba de forma secuencial.

Para publicar, leé `docs/releases.md`. El bundle usa una lista explícita de archivos; perfiles, `.env`, logs, adaptadores personales y datos de usuarios quedan fuera. La versión se declara en `Cargo.toml` y su entrada de `Cargo.lock`. El tag debe coincidir con ella.
